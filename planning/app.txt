0. Instructions to Antigravity (read first)
You are building a two-part system:
1. Android app (Java) — installed on the parent's phone only.
2. Python backend service — handles transcription, intent understanding, task
preparation, and emergency detection.
Ground rules for this build:
No real-world irreversible actions. Food ordering and cab booking are
simulated/mocked in this scope. Do not integrate real Zomato/Swiggy/Uber/Ola APIs
— generate a MockExecutionService that returns a fake confirmation after a short
delay, as if a real order/booking succeeded.
Every non-emergency task requires explicit parent tap-to-approve before
"execution." Nothing fires automatically.
Emergency events bypass approval entirely — see Section 6.
Favor clarity and modularity over cleverness. Comment generously — this is a
personal project the author will maintain and extend themselves.
Where a real capability is legally/technically out of reach in a generated prototype
(e.g., silently recording live phone calls on modern Android), flag it clearly in code
comments and in a KNOWN_LIMITATIONS.md rather than faking a workaround.
Do not fabricate working API keys, secrets, or credentials. Use .env /
local.properties placeholders ( OPENAI_API_KEY=your_key_here ) and
.gitignore them.

1. Call Capture (author's decision: automatic, on-device, triggered by
registered number)
Confirmed design: When a call comes in from a phone number matching a registered

ChildProfile.phone_number , the app automatically captures the call audio on the parent's

device — no manual step from the parent. The audio file is then auto-uploaded to the
backend for Whisper transcription (Section 5). Nothing is transcribed on-device.
Build it this way, but be honest about the platform ceiling:
Antigravity should build the call-detection layer using PhoneStateListener /
TelephonyManager (or CallScreeningService on Android 10+) to detect call
start/end, duration, and match the incoming number against
ChildProfile.phone_number .
Automatic call audio capture is genuinely restricted on modern Android (10+)
unless the app holds the default Dialer role, and even then behavior is inconsistent
across OEMs (Samsung, Xiaomi, Pixel all differ) and is disallowed in some
regions/carriers entirely. Build NativeCallRecordingSource as the primary
implementation, requesting the default-dialer role during onboarding and using
MediaRecorder / CallRecordingService where the OEM permits it.
Build a ManualUploadAudioSource as an automatic fallback, not the primary path: if
NativeCallRecordingSource fails to produce a file after a call ends (permission
denied, OEM blocks it, etc.), surface a lightweight in-app prompt asking the parent to
share a call-recording file from their device's native recorder — this keeps the pipeline
unblocked on devices where silent capture doesn't work, without changing the
intended "automatic" UX on devices where it does.
Add a "How call capture works on your device" info screen during onboarding, and a
one-time compatibility check that tells the parent up front whether their specific
phone/OEM supports automatic capture, so expectations are set correctly before they
rely on it. This remains the single riskiest technical assumption in the whole build —
test it early on Adi's actual device/carrier before building anything downstream of it.

GPT intent-extraction prompt (embed this in the backend, adjustable):
"You are a task-intent classifier for a child's phone call to their parent. Given this
transcript, output STRICT JSON only: category (food/cab/none), summary_text (one
plain sentence a busy parent can read in 2 seconds), details (object), confidence (01), is_emergency (bool), emergency_reason (string or null). Treat distress, fear, pain,

or safety threats as emergencies — bias toward false positives over false negatives for
emergency detection."

6. Emergency Detection & Bypass (Phase 2 — critical path)
Emergency classification happens inside the same GPT call as intent extraction (see
prompt above) — keep it a single call to avoid latency doubling, but log both signals
separately.
On is_emergency: true :
1. Skip the approval pipeline entirely.
2. Fire an FCM high-priority notification that opens EmergencyAlertActivity
even over lock screen.
3. Trigger FusedLocationProviderClient to grab the child's phone's last known
location if the child's device also has a lightweight companion component —
flag clearly that this requires the child to have some app or SMS-based location
share; a completely offline keypad phone cannot provide GPS. Document this
gap explicitly.
4. Start a backend timer (e.g., 3 minutes); if the parent hasn't acknowledged via
/emergency/{id}/acknowledge , send a second push notification (FCM) to the
backup contact. No Twilio/SMS for now — this means the backup contact must
also have the app installed with a registered device token (they can be added as a
lightweight "guardian" profile with no children of their own, just a notification
target). Flag this as a real limitation: an offline/non-app backup contact cannot
be reached in this version. Twilio SMS escalation is a clean Phase 3 add — build
the escalation logic behind a NotificationChannel interface so swapping in
SMS later doesn't require touching the emergency-detection logic.
Because false positives here are costly (crying wolf) and false negatives are
dangerous, build a simple admin review flag: every emergency event is stored and
reviewable in a History filter, per masterplan's "log and review to refine" mitigation.

6a. Approval-Strictness Rule Engine (Phase 2, confirmed logic)
Two modes for now (design the enum so a third tier can be added later without a schema
change):
always_approve — every non-emergency task sits as pending until the parent taps

Accept/Decline. No timeout auto-action. This is the default for younger children.

auto_approve_under_threshold — the parent sets auto_approve_max_amount (e.g.

₹300) and auto_approve_timeout_minutes (parent-configurable, e.g. 2 or 5). When a

task's estimated cost (from GPT's details.cost ) is at or under the threshold:
The approval card still fires immediately, same as always.
A backend job starts a auto_approve_timeout_minutes timer alongside it.
If the parent hasn't responded when the timer fires, the backend auto-approves
the task, sets decision_source = "auto_timeout" , and runs
MockExecutionService . If cost is above the threshold, no auto-approve timer
runs regardless of mode — it behaves like always_approve for that task.
Any parent response (Accept/Decline) before the timer fires cancels it and sets
decision_source = "manual" .
History screen should visually mark auto-approved tasks differently (e.g., a small
"auto-approved" tag) so the parent can spot them at a glance and adjust settings if
they're unhappy with what got through.

8. Security Requirements (Phase 1 + 2)
Caller verification, two layers: (1) incoming number matches
ChildProfile.phone_number ; (2) Resemblyzer voice-embedding cosine similarity
above a threshold (Phase 2).
All backend endpoints require a Firebase Auth JWT tied to the parent account; a child
profile can only be accessed by its owning parent.
Encrypt voice_embedding and any stored transcripts at rest (SQLCipher for SQLite,
or Postgres native encryption later).
Rate-limit /calls/upload per child to prevent abuse.
All secrets via environment variables — never hardcoded.

11. Decisions Log
Call capture: Automatic, on-device, triggered when a call comes in from a registered
child number. Audio is auto-uploaded to the backend for Whisper transcription (not
transcribed on-device). Manual upload is a fallback path only, used if native capture
fails on a given OEM/device.
Emergency escalation: Push notification only for now (no Twilio/SMS). The backup
contact must have the app installed as a "guardian" profile to receive it. SMS escalation
is deferred to Phase 3, built behind a NotificationChannel interface so it's a clean
swap-in later.
Approval strictness: Two concrete modes — always_approve and
auto_approve_under_threshold (with a parent-set cost threshold and timeout,
default 5 minutes). See Section 6a for full logic.
Still genuinely open — worth deciding before/while building
Which device/carrier will you test native call-recording on first? This tells you early
whether you'll be relying on the manual-upload fallback more than you'd like.
Should the compatibility check (Section 1) run once at onboarding only, or re-check
periodically in case an OS update changes what's allowed on that device?
For a guardian-only backup contact profile, do they need their own login, or can they
just register a device token via a lightweight invite link (no full account)?
